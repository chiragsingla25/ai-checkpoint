## Extra checks
- **Criterion 13 wording.** `python -m ai_checkpoint.cli ...` is a silent no-op (exit 0, no output) because cli.py has no `__main__` block. It meets the criterion as written but proves nothing. The meaningful check above used `python -m ai_checkpoint` and the console script. Suggested fix: add `if __name__ == "__main__": raise SystemExit(main())` to cli.py so the documented command does what it says.
- **msvcrt retry loop.** If `msvcrt.locking` raises OSError immediately for some reason other than contention (for example EBADF or EINVAL), the loop spins with no sleep for 60 s and then raises a "timed out" StoreError that hides the real error. With contention this does not happen, because LK_LOCK itself waits about 10 s per call. Consider a short sleep in the loop and keeping the last OSError as the `__cause__`.
- **60 s cap.** On Windows a save waiting on the lock gives up after 60 s with StoreError. fcntl blocks forever. I accepted this as "retries until acquired" with a bounded wait. The build log lists it as a user-visible change.
- **New stores get `core.autocrlf=false`** written to their local `.git/config` (`git config --local --list` shows `core.autocrlf=false`). Stores created by the old code don't get it, but the `-c` flags cover them. The old code still saves into a store created by the new code (cp-004).
- **Files the builder did not mention:** none. The diff touches only README.md, cli.py, store.py and the new tests/test_windows_sim.py. The missing-mcp message belongs to F-002 and was not done here, which is correct.

## Regression sweep
Code paths touched: `GitStore._git` (adds `-c core.autocrlf=false -c core.safecrlf=false` and `errors="replace"`), `GitStore._ensure_repo` (local autocrlf=false at init), `GitStore._lock` (fcntl branch restructured, new msvcrt branch, no-op fallback), and `cli.main` with the new `_force_utf8()` (reconfigures stdin/stdout/stderr to UTF-8).

HEAD was checked out with `git worktree add <scratch>/old HEAD` and removed afterwards.

1. **CLI sweep, identical.** I ran the same script against both versions on fresh stores. It covered: list on an empty store; save from a file, from a Unicode file, and from stdin with resumed_from and CRLF/tab content; save with malformed JSON, a missing file, and a JSON array; list, `list --chat trial`, `list --chat none`; and get and resume for refs `cp-001 cp-2 v1 forecasting/v1 FORECASTING/V1 trial/uni uni chat\name missing '' cp-999`. I also compared git log subjects, name-status, and porcelain status. After normalising commit hashes and timestamps the output was identical, apart from file sha256 values that differ only because created_at differs.
2. **API and MCP with a fixed clock, identical.** I saved three checkpoints with both versions using a fixed clock. They included resumed_from, `café ✓ 日本\r\n`, a redacted API key, and a non-ASCII chat name. Byte-for-byte identical across versions: the sha256 of every checkpoint file, commit subjects, commit tree hashes, `list().to_dict()`, the rendered briefs, the MCP `list_tools()` schemas (names, descriptions, inputSchema), the server instructions, and the `resume_checkpoint`, `get_checkpoint` and `list_checkpoints` tool results. The diff of the two JSON dumps was empty.
3. **Cross-version stores.** The new code saves into a store created by the old code, and the old code saves into a store created by the new code. Both work.
4. **REGRESSION in the CLI error path.** `_force_utf8()` calls `stream.reconfigure(encoding="utf-8")` without passing `errors`, and that resets stderr's handler from `backslashreplace` to `strict`. Any error message containing a lone surrogate, such as a command-line argument with bytes that are not UTF-8, now fails to print:
   - HEAD: `python -m ai_checkpoint save --file $'\xff.json'` prints `error: cannot read \udcff.json: [Errno 2] No such file or directory: '\udcff.json'` with rc=1.
   - New: the same command prints `object repr : UnicodeEncodeError('utf-8', "error: cannot read \udcff.json: ...", 19, 20, 'surrogates not allowed')` and `lost sys.stderr` with rc=1. The user never sees the error message. I reproduced this under the default locale, `LC_ALL=C.UTF-8` and `LC_ALL=C`.
   - `get $'\xff'` is not affected, because NotFoundError uses repr(), which escapes the surrogate. The `save --file` error messages (cannot read, not valid JSON, must contain a JSON object, nested too deeply) are affected, because they put `args.file` into the message unescaped.
   This input worked before and is not required by any criterion, so under the policy it is a FAIL.

## For the builder (FAIL only)
1. **stderr error handler reset by `_force_utf8()` (src/ai_checkpoint/cli.py).**
   Reproduce: `AI_CHECKPOINT_HOME=$(mktemp -d) python -m ai_checkpoint save --file $'\xff.json'`. It prints `lost sys.stderr` instead of `error: cannot read \udcff.json: ...`.
   Correct behaviour: the same message HEAD prints, with exit 1. Keep each stream's existing error handler when switching the encoding, for example `reconfigure(encoding="utf-8", errors=stream.errors)`. Alternatively set `errors="backslashreplace"` on stderr. Then cp1252 consoles still get UTF-8, and a surrogate in a message no longer breaks stderr. A test that runs the CLI subprocess with a non-UTF-8 `--file` argument and asserts `b"cannot read" in stderr` would cover it.
2. Optional, not a fail: add a `__main__` block to cli.py so `python -m ai_checkpoint.cli` (the command named in criterion 13) actually runs. Add a sleep, and keep the last OSError as the cause, in the msvcrt retry loop.
