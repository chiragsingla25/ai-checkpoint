## Notes (design gaps later features will hit; not FAIL causes)
1. **Id allocation drops git-history numbers (regression risk for F-002).** Today `_next_id` = max(files in checkpoints/ + numbers seen in `git log --name-only -- checkpoints`) + 1, so an id whose file was deleted is never reused. §4 says next id = max over cp-N.json files and bundle dirs only. If F-002 follows the doc literally, deleting the newest checkpoint file (outside the tool) lets its id be reused, which today's tests may cover. The git-log scan also only looks under `checkpoints/`, so it must be extended to `chats/*/checkpoints/`. Doc should say "files, bundle dirs, and every id ever committed under either path".
2. **Chat folder collision is possible.** A chat literally named `my-chat-674b8505` gets slug==key, so no suffix, and lands in the same folder as `My Chat` (verified with the stated algorithm; same for a chat named `chat-715fd30f` vs `預測`). Two different chats would share one events.jsonl. §4's "effectively impossible" is wrong for adversarial/coincidental names. Fix: always suffix when the key matches `-[0-9a-f]{8}$`, or check the folder's manifests' chat key and disambiguate. Also the §4 example hash `3f9a21c4` is illustrative; the real value is `674b8505` — tests should not copy the doc's example.
3. **Underspecified points F-003/F-004/F-005 will have to decide:**

Also unstated whether check 4 (and check 1) runs on carried-forward parent decisions/tasks or only on items supplied in this save; carried old-format decisions with empty rejected could make a resumed save unfixable.
