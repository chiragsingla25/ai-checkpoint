## Notes (not failure causes)
1. **`plan_updates[].depends_on` says the wrong thing (fix recommended).** The MCP schema reuses `FD["tasks.depends_on"]`: "Numbers of tasks that must be done first, e.g. ["t-1"]. Task k in your list is t-k." In `plan_updates`, ids are real lineage ids, which is correct per DESIGN §11. A model following the text gets a silently wrong dependency. Reproduction: resumed_from cp-003 (t-1..t-5), `plan_updates [{text x}, {text y, depends_on ["t-1"]}]` (meaning "after x") -> saved, with y depending on the parent's t-1 (done), not on x (t-6). It needs its own field description, e.g. "Ids from the brief (e.g. "t-2"); a new task in this list gets the next id after the highest one in the brief." This is the same class of problem as F-003 attempt 1.
2. The flat `next_steps` view lists done tasks too (e.g. `User's plan: backtest` after it is done). This has been so since F-003 and is unchanged here. The bundle brief is correct.
3. Carried workspace `done_with` items pile up over a chain (they are never dropped). That is by design (merge by key), but "No longer needed" will grow over long chains.

## Objection (scope of criterion 4)
- **Criterion:** "Unmentioned parent decisions, facts, workspace and user_turns are carried forward unless replaced; the events.jsonl line records resumed_from."
- **The problem:** it doesn't say which resumed saves carry forward. The DESIGN §11 approved at F-001 says "Everything else carries forward from the parent unless the save supplies its own", with no exception. In F-005 the builder added "Only to a *structured* save (tasks, plan_updates, user_turns or facts) that has resumed_from. An old-fields-only resumed save behaves exactly as before (nothing is carried)." The reason given is to keep old-field-only resumed saves byte-identical.
- **Evidence:** `resumed_from=cp-003, next_steps=["go on"]` -> parent decisions d-1/d-2, facts, user_turns, workspace, open_questions and verbatim are all dropped. Adding `user_turns: ["ok go"]` carries all of them.
- **The trade-off:** carrying for old-only saves protects a resumed chat that uses the old form (still documented as working) from silently losing the parent's decisions and workspace. But such a chat usually restates the parent's decisions, and with "supplying decisions adds" that would duplicate them. Not carrying is today's behaviour, so it is no regression, and the tool text steers resumed chats to `plan_updates`.
- **Proposed wording (pick one):**
  - (a) "...are carried forward unless replaced, for any save with `resumed_from` that gives structured fields (`tasks`, `plan_updates`, `user_turns` or `facts`); an old-fields-only resumed save behaves as before." -> the current build passes.
  - (b) "...are carried forward unless replaced, for every save with `resumed_from`, including old-fields-only saves." -> the current build fails this. It needs the one-line `carry` change in `store.save`, plus a decision on how restated decisions are deduplicated.
