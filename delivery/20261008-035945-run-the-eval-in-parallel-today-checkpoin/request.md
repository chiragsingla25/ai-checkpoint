# Request

Run the eval in parallel. Today checkpoint-eval suite/run make all model calls strictly one after another. Add a --workers N option (default 8; 1 = today's sequential behaviour; 0 or negative exits 2) to both run and suite that uses a thread pool (the model calls are network-bound; the OpenAI/Anthropic SDKs are synchronous, so threads are fine) to run independent calls concurrently: all scenarios in a suite run concurrently; inside a scenario the compaction call and the summary call run concurrently, the full_history answer call does not wait for either, and each variant's judge call starts as soon as its own answer is back (critical path = 3 calls per scenario). The total number of model calls in flight never exceeds --workers. Results must be identical to a sequential run: results.json, results.md and handover files byte-identical between --workers 1 and --workers 8 with FakeModel, and stdout tables printed in the same scenario order. The progress counter must stay correct and lines must not interleave mid-line. Timeouts and the single retry keep working per call. A failure in one scenario must not stop the others. Verify the speed-up offline with the FakeModel delay env (CHECKPOINT_EVAL_FAKE_DELAY): e.g. the 6-scenario dataset with delay 0.5s takes about 24s with --workers 1 and under 5s with --workers 8. Product code (save/resume/MCP server) must not change.
