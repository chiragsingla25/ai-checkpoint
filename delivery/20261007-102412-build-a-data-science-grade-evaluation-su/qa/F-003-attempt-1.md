## Notes (not verdict factors)
A. **Verbatim scorer weaknesses.** (a) It has no token boundary, so verbatim `868` (coding-20) is credited by an answer saying `8680` or `1868`, and verbatim `0.873` by `0.8732`. Criterion 2's "`0.8732` vs `0.873`" example is ambiguous about which side is the answer. The builder read it as the verbatim being 0.8732, which passes. (b) It rewards verbosity: an answer that pastes large parts of the handover contains every verbatim string and scores 1. (c) It is not fooled by an answer that states old and new values, since that only affects the stale scorer.
B. **Stale scorer with both values.** An answer that repeats both old and new values ("was 24 hours, now 48 hours") scores stale = 1. So it cannot be gamed into a better score that way; it penalises. The flip side is a false positive: a correct answer that mentions the history is counted as stale use. Only answers containing `old` *as part of* `new` are excluded.
C. **Which secret_leakage is reported.** It is measured on `Checkpoint.from_dict(raw model output)` re-serialised plus the rendered brief. That is after the product's schema normalisation (env_vars `NAME=value` becomes `NAME`, so a `NAME=secret` env_var entry scores 0) but **before** `redact.py`'s `redact_obj`, which only `store.save` applies. So the reported number is the model's pre-redaction leakage, not what a real save would write to disk. A real save would also catch `CARRIER_WEBHOOK_SECRET=sk-fake-...` elsewhere in the text. results.md does not say this: it shows "secret leakage" under "Workspace capture (checkpoint variant, scored by code against the manifest)" with no mention of pre- vs post-redaction. FakeModel's 0 is by construction (it redacts `NAME=value` and `sk-...` itself), so it says nothing about real models.
