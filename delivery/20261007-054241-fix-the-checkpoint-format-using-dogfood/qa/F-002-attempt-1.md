## Extra checks
- **`status` is required (requested check).** It does not conflict with any written criterion. Criterion 1 says "every item carries a status of `still_relevant` or `done_with`". Criterion 2 lists unknown status and missing path/name as errors and does not say a missing status should get a default. It is also not a regression: old checkpoints have no workspace, and the old code had no workspace input. Consequence: a model that omits `status` on any one item has the **whole** save rejected. Through MCP, pydantic raises `ToolError: 1 validation error for save_checkpointArguments workspace.repos.0.status Field required` and nothing is written. Through `Store.save`/CLI it is `ValidationError workspace.repos[0].status: is required`. The tool schema marks `status` as required with an enum on every Ws* model, so schema-following clients should supply it, but one forgetful item loses the whole checkpoint. This is a note, not a FAIL. A lenient alternative, if the owner wants one, is to default a missing status to `still_relevant`; that is a criterion change for the owner to decide.
- Unknown workspace categories (e.g. `{"unknowncat":[...]}` or `{"foo":1}`) are silently ignored rather than rejected. This matches the "unknown keys are ignored" policy elsewhere. Note only.
- An env var given as `" export  FOO = bar "` is stored as name `export  FOO`. The value is dropped, but the `export` prefix stays in the name. Minor.
- MCP `save_checkpoint` input schema: the `required` list is unchanged from HEAD (`chat_name, checkpoint_name, current_step, next_steps, objective`). `workspace` is a new optional property.
